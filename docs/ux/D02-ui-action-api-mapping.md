## Feedback-state definitions

| State profile | Required design coverage | Evidence boundary |
|---|---|---|
| READ | Initial and applicable incremental loading; valid empty/no-match versus unavailable data; populated success; failed initial/partial/incremental loads with explicit retry; stale/aborted data must not replace current scope | Do not assume an empty list means no permission or missing entity; contract-dependent distinctions remain gaps |
| WRITE | Validation, draft/dirty, submitting/saving, disabled/readonly conditions, confirmed success, failed field/form save, uncertain outcome and close-during-save behavior | Required empty state is N/A for submission itself; nullable clearing and option-empty states are mapped separately |
| AUTH | Input validation or context checking, pending state, confirmed session/navigation, invalid/expired/rejected context and recoverable failure | Never imply delivery, account existence, revocation or credential validity beyond evidence |
| BOARD | Resting, keyboard/touch pickup, valid/current/invalid destination, provisional move, cancellation, confirmation, rollback and uncertain reconciliation | Status movement is evidenced; reordering, arbitrary transitions and conflict-free writes are not |
| UNIMPLEMENTED | No existing UI or confirmed browser contract; current feedback states N/A | Conditional future design states are proposals only; do not create committed delete flows without D-03 approval |

Permission feedback must distinguish confirmed readonly, loading/unknown permission, denial and session expiry when evidence supports those distinctions. Status code alone may not identify the exact cause. Announce progress and failures without depending on animation or color.

## Action dependencies and entity implications

- User/session (EN-01) underpins protected navigation. Session restoration is not evidence of a universal automatic refresh/retry policy for every failed request.
- Project list OP-08 and detail OP-24 establish context (EN-02); dependent screens must distinguish project loading/error from their own content loading/error.
- Member lookup OP-11 supplies assignment options (EN-03). Keep membership-record IDs separate from user IDs. An options failure must not silently clear an existing assignee.
- Epic list/detail OP-14/OP-16 supply task epic selection and context (EN-05); task writes check project relations. No cross-project epic selection is approved.
- Task create/edit OP-21/OP-22 act on EN-06. Task detail OP-29 has normalized display relations and independent canEdit; a known entity does not imply edit permission.
- Invitations (EN-04) can lead through authentication back to acceptance; an accepted response may lack a destination ID. No pending-invitation management entity or default selectable role is established.
- Statistics (EN-07) are read projections. OP-27 accepts project/status filters; OP-28 dates only. Calendar presentation does not imply editable scheduling, event CRUD or a distinct calendar API entity.
